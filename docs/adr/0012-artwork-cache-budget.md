# 0012 图片缓存按字节预算淘汰

- 状态：已采纳
- 日期：2026-11-19

## 背景

`internal/media` 把远程图片按 `sha256(url)` 命名存进用户缓存目录，解码后的位图存在 `Loader.entries` 里供页面直接取用。两者此前都只增不减：磁盘文件除了单张 12 MB 的上限外没有任何预算，`entries` 里的 `*ui.Bitmap` 更是永不移除。发现页、资源库、搜索页浏览得越多，磁盘与内存就越大，重启后磁盘部分照旧，进程内的位图随浏览累积。

上游图片来自源规则返回的海报与横幅，URL 带签名与尺寸参数，同一个影片在不同页面可能给出不同地址，所以「按影片去重」并不可行；能约束的只有总量。

主流实现的做法分两类。Coil 按可用磁盘的 2% 取预算并夹在 10–250 MB 之间，Glide 由应用传入固定字节数并用带 journal 的 `DiskLruCache`，SDWebImage 默认不设磁盘上限而按 1 周的 `maxDiskAge` 过期、访问时间可配成 `accessDate`。Kodi 的 `CTextureDatabase` 走另一条路：它把纹理登记进 SQLite，清理时用 `CImageCacheCleaner::ScanOldestCache` 取最旧的若干条，再与视频库、音乐库、插件库比对，只删「不再被任何库引用」的——因为它知道哪些图片是库的一部分。

## 决定

磁盘与内存各设一份字节预算，都按最近使用时间淘汰，都用 `Options` 暴露（零值取默认、负值表示一份都不留）。

磁盘默认 128 MiB，单张仍受既有 12 MB 上限约束。访问即更新 mtime（`Loader.read` 命中后显式 `os.Chtimes`，不依赖文件系统的惰性访问时间），写入走临时文件再 `os.Rename`，写完立即在持锁状态下扫描目录做一次淘汰，`New` 时也扫一次把上次进程留下的超额部分收掉。淘汰时按 mtime 升序删，跳过刚写入的那个文件。只有 `.img` 后缀参与统计与淘汰，临时文件不算。

内存默认 96 MiB，成本按解码后的像素计（`width * height * 4`），`Bitmap()` 每次被页面取用都刷新使用时间。超预算时把最久没被取用的位图从 `entries` 里删掉；页面再次要它时走磁盘缓存重新解码，不再走网络。加载失败的条目留在表里：它不占内存，而留着才能记住这个 URL 是坏的、不再重试。

不做 SQLite/journal 索引，也不用「引用计数」：URL 到文件名的映射是纯函数（`sha256(url)`），目录本身即索引，进程被杀后重新扫描就能得到完整的用量与老化顺序，不需要一份可能与文件不一致的账本。这一点与 Glide 的 `DiskLruCache` 和 Kodi 的纹理库不同——它们需要账本是因为文件名不是内容的函数，且需要知道哪些条目仍被媒体库引用。Luvia 的图片绝大多数来自浏览页面而不是本地库，引用计数只能删掉一小部分，约束不了总量。

## 后果

缓存总量从此有界：磁盘最多约 128 MiB（按本机实测的平均 67 KB 一张，约 1900 张海报），进程内位图最多约 96 MiB（按 600×900 一张约 1.3 MB 计，约 70 张）。代价是被淘汰的图片再次出现时要重新解码一次（磁盘命中，不走网络），以及浏览很快时会有反复的解码开销——`ui.Bitmap` 的 mip 层级与 GPU 上传副本不计入内存预算，真实占用是这个数的倍数，若实测内存压力明显应下调默认值而不是把开销算进预算。

`os.Chtimes` 在每次磁盘命中时多一次系统调用，代价可忽略，但意味着老化顺序取决于「读」而不是「下载」，这正是不想回退进度时被淘汰所期望的顺序。

预算是代码里的常量而不是设置项。要变成用户可配时，`Options` 已经就位，只需在设置页读写；届时还应给出「清空图片缓存」的动作，因为预算一旦调小，淘汰发生在下一次写入或下次启动，而不是立即。
