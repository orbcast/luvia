# 0002 分层 Agent 规则与自维护预算

- 状态：已采纳
- 日期：2026-11-16

## 背景

这个仓库主要由 Agent 推进，规则文件实际上是"协作宪法"。单文件写全所有内容会立刻失控：跨技术栈的底线、MyGo 的线程与测试约束、某个模块的构建细节混在一起，Agent 要么读漏，要么把 MyGo 的限制套到未来的 Swift 应用上。经验上，散文规则还有两个必然退化：条数只增不减，以及规则与代码悄悄分叉——本轮就出现过 `apps/desktop/AGENTS.md` 已要求"文案走 catalogs"、而 `apps/desktop/main.go` 仍写死中文字面量的情况。

## 决定

规则按目录分层：根 `AGENTS.md` 只写跨应用底线（职责归属、解耦方向、交付诚实、测试分级、提交纪律）；`apps/<name>/AGENTS.md` 只写该应用的技术栈、线程模型、构建与验证；`packages/<name>/` 自备边界说明。子目录可细化，不得降低根目录要求。

规则要可修剪，所以带三条硬约束：能脚本化的条款必须落进 `scripts/check-rules.py` 并由 `make check` 执行，不靠"请遵守"；根 `AGENTS.md` 不超过 9000 字符、其他 `AGENTS.md` 不超过 6000 字符，超出时先合并或删除失效条款再补新规则；发现规则与代码冲突，在同一次变更里改掉其中一方，不把矛盾留给下一个人。

## 后果

新增规则的成本变高，这是故意的：写不进检查、也说不清谁来执行的规则，通常不该存在。体量预算会逼着把细节下沉到 `docs/` 或 ADR，根文件保持"能一次读完"的长度。检查脚本本身成为规则的一部分，误报要改脚本或改代码，不能靠忽略绕过；脚本没有覆盖的条款仍然靠人和 Agent 遵守，这一点在 ADR 0006 里明确划出边界。
