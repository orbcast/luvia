# 0021 发布包内置封装的访问密钥

状态：已采纳，部分取代 [0019](0019-access-keys-in-the-app.md)
日期：2026-11-27

## 背景

[0019](0019-access-keys-in-the-app.md) 决定密钥不随安装包下发，用户自己在设置页填。它的理由是「公开仓库里的密钥等于公开」和「泄露后无法撤回」，两条都成立。但它没解决分发问题：不认识的人装完看到的是「数据源加载失败」，还得先想办法弄到密钥，而这个来源作者并不能控制。

于是问题变成选择题：要么接受「装完不能用」，要么接受「密钥公开」，要么中间有一条路。

## 决定

发布包内置一份**封装的**密钥：构建时 `cmd/seedpack` 把它封成 `kanju.seed`，放进产物的 `luvia-rules/` 旁边；启动时 `preferences.SeedValue` 打开它，作为最低优先级的密钥来源写进进程环境。优先级从高到低是：进程环境（shell 导出）→ `secrets.json`（设置页）→ 内置种子。用户随时可以用后两者覆盖掉内置的那份。

封装方式：AES-GCM，密钥来自**构建时注入的随机盐**（GitHub 仓库变量 `LUVIA_SEED_SALT`，每次发版不同），盐缺失时构建不带种子而不是带一个可猜的种子。文件格式是版本字节 + nonce + 密文，任何一项不对就整份打不开，不会半解出垃圾去签名。

## 后果

**这一条必须说在最前面**：种子挡的是「打开压缩包就能读到」，不是「拿到密钥」。程序为了签名请求必须在内存里持有明文，能在这台机器上跑调试器的人就能读到它，OWASP MASWE-0005 与 Android 官方文档对每个内置凭据的客户端给的都是同一结论。随机盐让每次发版的封口不同，所以泄露属于某一次发版，换盐重发即可止损；但已经不洩漏过的密钥换不回来。

因此仍然存在的风险：拿到产物的人可以逆向出密钥，用它绕过这个应用直接请求上游；上游若因此拉黑，受影响的是所有装了那一版的用户，只能发新版补救。作者没有服务器来中转，也就没有「密钥根本不在客户端」这条路可走——那条是唯一能真正挡住逆向者的方案。

换来的是装完即用：不认识的人下载、打开、直接播放，不需要设置页、不需要命令行、不需要作者把密钥贴在哪里。`sessions.json` 的匿名会话照旧自动申领，用户无感。

仓库保持干净：盐只存在于仓库变量，密钥只存在于 `secrets.KANJU_SECRET`，两者都不进版本库，`.env` 与 `.gitignore` 的既有边界不变。开发构建（不带 `prodseed` 标签）用源码里的开发盐，本地 `make dev` 行为不受影响。

重新评估的触发条件：上游因密钥滥用而封禁、`seedpack` 的盐被误提交、或者作者有了自己的服务器——那时把签名挪到服务端，客户端只持会话，才是真正的解法。
