# 0001 应用与共享模块分离

- 状态：已采纳
- 日期：2026-11-16

## 背景

Luvia 计划长期演进为视频播放器，可能同时存在 Go + MyGo 桌面应用与 Swift / SwiftUI 应用（或更晚的其他端）。这些应用的技术栈、身份配置、构建与发布节奏各不相同；把可运行的一切塞进单个工程，或提前抽一个"万能核心库"，都会让第一个真实功能到来之前就产生耦合。

## 决定

可运行、可构建、可发布的代码放 `apps/<name>/`，各自维护语言、依赖、身份配置与验证入口，互不导入内部实现。只有出现至少两个真实消费者时，才提取 `packages/<name>/`，并在该模块的 README 与 `AGENTS.md` 中写明语言、平台、兼容范围和检查方式。当前没有任何共享模块，因此不预建空包、空接口或无消费者的抽象层。

非应用目录各自有明确职责：`apps/luvia-rules/` 保持自包含的源规则与资源源，便于随时拆仓；`assets/` 放跨应用共享的素材母版；`scripts/` 与根 `Makefile` 是开发入口。

## 后果

应用之间复制少量启动与身份配置是可接受的代价，换来的是任一端可以独立删改、独立发版。反过来，任何"共享"诉求都必须先给出两个真实调用点，否则留在应用内。当某个契约被两个以上应用实际使用，再提取模块并以 ADR 记录边界；提取时允许保留应用内适配层，核心不反向依赖具体 UI 或系统能力。
