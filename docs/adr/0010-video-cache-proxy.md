# 0010 视频经本地缓存代理播放

- 状态：已采纳
- 日期：2026-11-17

## 背景

播放页把源规则解析出的地址直接交给系统视频组件，重复观看每次都重新走网络。规则引擎按 [ADR 0008](0008-rule-dsl-and-engine.md) 不缓存直链，缓存属于上层。实际上游的线路几乎都是 HLS，而且有的把 `.m3u8` 地址错误地标成 `mp4`，此前 `inferURLKind` 以声明优先，导致界面与日志显示的类型与实际不符。

用户需要"看得见的视频缓存"，同时不能把 mp4 与 HLS 做成两套通路。系统播放器（AVFoundation / GStreamer / Media Foundation）本身会解码与缓冲，应用层缺的是把播放过的字节留在本地、下次不再下载。

## 决定

新增 `internal/videocache`：在 `127.0.0.1` 上起一个回环 HTTP 代理，把远程播放地址改写为代理地址，播放器照常打开它。代理在 HTTP 层透明，mp4 与 HLS 共用一条通路，不需要应用自己解析媒体。

缓存键为 `sha256(upstream url)`，对象整块下载后用临时文件原子替换落盘；同一 URL 的并发请求由单飞合并成一次下载；缓存按字节预算做 LRU 淘汰（默认磁盘上限 2 GiB、单个对象上限 512 MiB），启动时扫描目录大小。HLS 播放列表被改写：所有 URI（子清单、分片、`EXT-X-KEY`、`EXT-X-MAP` 等）都指向代理，分片与密钥同样被缓存。超过单对象上限的大文件不缓存，直接带 `Range` 透传给上游，保证大文件拖动仍然可用。命中缓存的文件用 `http.ServeContent` 支持 `Range`。

播放器按范围读取的对象永远走不到"整块完成"，它的字节一直留在 `.cache.part` 里。`.part` 与完整对象一样计入预算、一样按读取时间老化、一样可被淘汰，只有正在传输的那个 part 在 `evict` 时被跳过——否则范围读取的字节既不占预算也不会被删除，缓存会在磁盘上无限增长而淘汰永远找不到可删的东西。

播放页在 `open` 时经 `Cache.ProxyURL` 改写地址；缓存对象为空（例如测试）或地址不是 http(s) 时退回原地址。系统组件已打开但首帧未到时，画面显示复用已有 `buffering` 文案的缓冲提示。

一集解析成功后，播放页在后台把下一集也解析一次并预热它的前几个分片：下一集用刚用过的线路，只取开头约三个分片，与当前播放共用同一套单飞与预算。预热只对 HLS 生效——单条媒体地址无法预知播放器要哪些字节，预取它等于把整部影片下载下来。观众已经切走（解析代号变了）就不再预热，也不为两集之后的剧集预热。

同时修正线路类型识别：新增 `playbackURLKind`，地址里的 HLS 信号优先于上游声明的 `mp4`，`inferURLKind` 只作单字符串判断与兜底。

## 后果

重复观看命中磁盘，HLS 的分片与密钥也会缓存，跨会话保留。代价是首次播放要先完整下载对象（清单与分片很小，基本无感；大于上限的文件不缓存只透传），以及缓存目录多占磁盘。预热的代价是切集时多一次线路解析和几段分片流量，可能和正在播放的缓冲抢带宽；如果实测发现抢带宽明显，改为只在播放稳定后再预热。

HLS 能否真正播放仍取决于系统解码器：macOS 的 AVFoundation 原生支持，Linux 需要 `gstreamer1.0-plugins-bad` 提供 hlsdemux。开发用的 Linux 环境未安装该插件且无 root，真实 HLS 在本机仍不能播放，这与缓存无关。

代理只在回环监听，仅放行 http/https。图片缓存（`internal/media`）仍是按 URL 累积、无淘汰，与本决策没有合并；容量与开关若要做成用户可配，放在设置页另议。
