# 0008 源规则用声明式 DSL，desktop 只做通用解释

- 状态：已采纳
- 日期：2026-11-16

## 背景

播放器的数据源来自 `apps/luvia-rules/`，该目录未来随时可能拆成独立仓库。上游站点各有签名、header、分页与线路兑换方式，若在 desktop 里为每个站点写一个 Go 适配器，规则就无法脱离代码发布，desktop 也会被迫认识具体的上游名称。另一方面，上游并不都长得一样：有的直链播放，有的需要二次兑换票据，有的是带 `maccms` 风格的 SDK 与解密。

## 决定

规则是纯数据 JSON，由 desktop 的固定解释引擎执行；DSL 用「按操作分块 + 步骤数组 + 命名变量」，取值用受限选择器（点路径、`[n]`、末尾 `[*]`）加闭集函数表，不引入 JSONPath、不内嵌 jq/JS/Lua。契约只有五个操作：首页、列表（含搜索）、详情、选集、解析。块存在即支持，缺块返回 `unsupported`，不做隐式兜底。

一个上游一个目录，目录名即源 ID；同一上游的多条播放源与线路是运行时数据（响应中的线路数组），不拆成多条规则。线路解析内建「映射 + 可选二次兑换 + 尝试顺序」，因为这种形状在多个站点重复出现，不是某个站点的特例。

代码分四个依赖单向的包：`internal/source`（契约、`Ref`、错误分类）、`internal/source/rule`（解码与校验）、`internal/source/engine`（解释器与 HTTP）、`internal/source/loader`（目录扫描、坏规则隔离、诊断、热重载）。引擎不缓存、不聚合、不自动续期直链；这些属于调用方。

规则目录路径只从配置读取，默认解析顺序为环境变量 `LUVIA_RULES_DIR`、用户数据目录的 `rules/`、应用包内 `Resources/rules/`。desktop 源码不出现上游名称，也不编译期嵌入规则。

## 后果

新增站点只需提交规则与 fixtures，不重新编译 desktop；拆仓后只需改变规则来源，不复制解析实现。代价是 DSL 表达力有上限：需要脚本、解密或非常规协议的站点无法接入，必须先在 DSL 里补通用能力，或明确放弃该源，而不是为它开后门。

规则必须自带 fixtures，`make rules-verify` 在本地离线跑通五个操作；真实网络的冒烟测试只作为手动检查，不能替代可重复验证。规则严格解码，未知键、未声明变量、非法字段名在加载阶段即被拒绝，坏规则被 loader 跳过并留下诊断，不阻塞其他源。

格式与字段说明见 [docs/rule-dsl.md](../rule-dsl.md)。若将来出现必须共享的规则执行器（第二个消费者），再按 ADR 0001 评估提取 `packages/` 模块。
