# 0014 让源规则同时吃 JSON 接口与服务端渲染页面

- 状态：已采纳
- 日期：2026-11-21

## 背景

规则 DSL 原本只有一种响应形态：请求回来的 body 就是 JSON，直接交给解码器。这套假设在红果短剧上不成立。它的搜索有干净的 JSON 接口（`/api/search/result`），首页、分类页与详情页却都是服务端渲染的 HTML：真正的数据塞在页面脚本的一条 `_ROUTER_DATA = {...}` 赋值里，外面包着整页标记。

一个上游只对应一个源目录，六个操作共用一份 `rule.json`，因此同一个源必须既能读 JSON 接口，也能读 HTML 页面。此外这六个操作本身也不对称：有搜索词时要走搜索接口，没有搜索词时要走分类页，同一个 `list` 块得在一次调用里二选一。详情页还有第三处麻烦——它只给一串 `vid` 字符串，没有任何集号字段，选集要的 `id` 与 `number` 只能从“第几个”推出来。

## 决定

`request` 增加 `response` 声明响应形态：缺省与 `"json"` 按 JSON 解析 body；`"routerData"` 先从 HTML 里抽出数据对象再解析。抽取按 `_ROUTER_DATA` 字面量定位，要求其后确实是赋值号 `=` 再跟 `{`（页面别处提到这个名字或只是读一下全局都跳过），从那个 `{` 起逐字节配平花括号（跳过字符串字面量与转义，标题里的花括号不会让对象提前结束），配平结果还要通过 JSON 校验才采用；页面里这个字面量出现多次，所以第一次配平失败就继续找下一次，全页都失败才报 `invalid_response`（"response carries no router data"）。抽取只负责拿到对象，结构对不对由后续选择器负责。

步骤增加 `when`：值求为真才执行，缺省总执行。求值为假或求值失败时该步不绑定任何变量，后续引用它的地方看到的是“变量缺失”。配套放开同名 `as`——带 `when` 的步骤是二选一的一个分支，只有它能和另一个分支共用一个变量名；不带 `when` 的重复绑定仍是规则错误。

`output.from` 支持候选回退，用 `|` 分隔，按序取第一个能解析出结果的候选，全部失败才报 `"%q is missing from the response"`。它和 `when` 是一对：两个分支绑同一个 `as`，`from` 列出各自响应里数组的位置，哪条真的跑了就读哪条。校验阶段每个候选都要单独站得住（能解析、根名在作用域、不许空候选），这样一个分支里的笔误不会被另一个分支盖住。

映射走过的每一项额外可读 `item`（该项本身）与 `index`（它在列表中的位置，从 1 开始），对象项仍然是字段查找优先，字段不存在时才落到这两个名字。列表项是纯字符串时这是唯一能读到的东西，红果详情页的 `vid` 数组正是这样映射成选集的 `id` 与 `number`。

新增两个函数：`empty`（值缺失、空数组、空字符串为真）与 `not`（布尔取反），配合 `when` 表达“没填搜索词”这类条件。

## 后果

DSL 多了三个概念（响应形态、条件步骤、候选回退）和两个内建名字（`item`、`index`），规则作者写一个源时要读懂页面结构：`_ROUTER_DATA` 在哪个脚本里、数据挂在哪一层、分页与选集字段叫什么。抽取逻辑只看花括号配平，上游把数据改成别的变量名或改成流式下发的 `self.__next_f`，规则与抽取代码都要跟着改，fixtures 也要重录。

`when` 让“变量一定存在”不再是块级不变量：一个条件分支没跑，引用它的模板会整个失败，`from` 会掉到下一个候选。规则作者要在两个分支上都给出可用的读取路径，否则只在其中一种输入下报错，这种错误在离线 fixtures 里要靠两组用例才覆盖得到。同名 `as` 的放宽只对带 `when` 的步骤生效，其余重复绑定仍在加载时被拒绝。

候选回退让 `from` 的错误信息带的是整串候选而不是失败的那一段，定位时得自己比对；这是有意的，两个候选都空本身就是“响应里没有预期结构”这一件事。

上游一旦提供稳定的 JSON 目录接口（首页、分类、详情都能直接给 JSON），`routerData` 就可以从规则里撤掉，退回到单一响应形态，抽取代码与相关 fixtures 一并删除；`when` 与候选回退仍然有用（搜索与浏览共用 `list` 块），届时只需重新评估是否还有第二个消费者，没有就一并收掉。`item` / `index` 与响应形态无关，只有上游开始给结构化集号时才可能不再需要。
