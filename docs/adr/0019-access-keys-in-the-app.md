# 0019 访问密钥在应用内填写

状态：已采纳
日期：2026-11-27

## 背景

kanju 规则用 `${env:KANJU_SECRET}` 描述签名密钥，引擎只用 `os.LookupEnv` 求值，密钥因此不落进安装包。这对开发机成立：`make dev` 从 `.env` 加载，终端里 export 也生效。对发布版不成立——Windows 从开始菜单启动、macOS 从 Finder 或 Dock 启动的进程不继承任何 shell 配置，用户装完打开就是「数据源加载失败」，报错是 `sign.secret "${env:KANJU_SECRET}" is not set in the environment`。

分发时的候选有三条：把密钥烤进安装包（对公开仓库等于公开发布密钥，且泄露后无法撤回）；让用户自己 export 环境变量（macOS 双击启动不读 `.zshrc`，`launchctl setenv` 还要重启登录会话，等于要求用户会命令行）；在应用内提供输入位置。前两条要么毁掉密钥，要么把「装好就能看」变成「先配环境」。

## 决定

设置页为规则声明的每个 `${env:NAME}` 提供输入框，值存进用户数据目录的 `secrets.json`（权限 0600），启动时在加载规则之前写进进程环境；进程环境里已有的同名变量优先，shell 导出的副本不会被文件覆盖。空输入表示不保存，从文件里删掉。

变量名由 loader 遍历规则得出，只读引擎真正展开的三个位置：`sign.secret`、`sign.headers[].value`、`http.headers[].value`。步骤自身的 path、query、body 与 exchange 的 path 会被解析成模板，`${env:X}` 在那里是非法选择器，规则加载时就被拒，所以变量不可能藏在模板里——这一点由测试固定，避免以后放宽模板语法时静默漏掉字段。

## 后果

用户装完即可在「设置 → 访问密钥」里填一次，不用碰终端；密钥仍然是明文文件，同账户的进程读得到，与任何本地配置处于同一威胁级别，要更强就得上系统钥匙串，本期不做。

密钥仍不随安装包下发，公开仓库保持干净；代价是每个用户要自己拿到密钥，应用无法验证填得对不对，只能等下一次请求返回 unauthorized 才暴露，因此失败页把「去设置里填密钥」明说出来。

`secrets.json` 只覆盖当前进程环境：填完后 main 会重建数据源页面，不用重启应用；但如果某个值在别处被改，进程内已设置的值要等重启才更新，因为 `ApplySecrets` 只补不存在的变量。

重新评估的触发条件：接入需要密钥的第二家源、用户需要多套密钥切换、或者要支持团队共享配置——那时把 `secrets.json` 换成系统钥匙串或配置导入导出更有意义。
